# Upstream base

This fork tracks [hiro-o918/rinkaku](https://github.com/hiro-o918/rinkaku).
This file records exactly which upstream state it is built on — the thing a
version number alone cannot say, since a merge rarely lands on a release
boundary.

**Update this file in the same commit that takes upstream in.** Nothing
enforces that; the record is only worth having if it is never stale.

## Taking upstream in

```sh
git remote add upstream https://github.com/hiro-o918/rinkaku   # once
git fetch upstream main
git merge upstream/main
```

Then, in the same commit:

1. update the table above (commit, date, versions, "taken in" date);
2. set `rinkaku/Cargo.toml`'s version to `<new upstream rinkaku version>+laravel.1`;
3. re-run `make test` and `make lint`.

A merge (not a rebase) is deliberate: the merge commit is what makes "which
upstream commits are already in" answerable by `git` itself, with this file
as the human-readable summary.

## What is *not* the fork's history

`rinkaku/CHANGELOG.md`, `rinkaku-core/CHANGELOG.md` and
`rinkaku-tui/CHANGELOG.md` are upstream's, generated by upstream's
release-please and frozen at the fork point (their latest entry is 0.6.22,
and every link in them points at `hiro-o918/rinkaku`). This fork removed
those release workflows, so nothing regenerates them.

They are left untouched on purpose — editing them would both misattribute
fork changes to upstream and create conflicts on the next upstream merge.
The fork's own history lives in `docs/adr/` and in its pull requests.
